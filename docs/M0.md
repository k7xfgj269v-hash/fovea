# M0 QEMU/KVM Harness

## Mental model and evidence boundary

M0 has two separate layers:

1. Task 007 supplies executable host checks, a reproducible QEMU command,
   QMP snapshot smoke testing, GDB register inspection, and a guest Intel PT
   probe.
2. Task 008 runs those tools on a physical Linux x86_64 host with real KVM and
   records the acceptance evidence.

This document covers the first layer. A successful dry run, fake QMP test,
Darwin/HVF run, mock transport test, or CI job proves tooling behavior only.
None is equivalent to task-008 physical acceptance. Do not claim M0 hardware
acceptance until a qualifying host has produced the required evidence.

The VM boundary is also the security boundary. The host-side supervisor and
its audit/gate policy are trusted. The guest, guest-agent, guest disk, and all
guest-originated responses, receipts, and telemetry are untrusted evidence.

## Prerequisites

The acceptance platform is:

- Linux on x86_64.
- A real, readable, and writable `/dev/kvm` whose
  `KVM_GET_API_VERSION` ioctl reports API version 12.
- `qemu-system-x86_64` with KVM, host CPU, `vhost-vsock-pci`, QMP over a Unix
  socket, a TCP GDB stub, `-nographic`, and the selected boot inputs.
- Python 3 for host preflight and `qmp-smoke.py`.
- GNU GDB for register inspection.
- Explicitly supplied guest artifacts. The harness does not download or
  create a kernel, initrd, disk image, symbols, or guest userspace.

For QMP `savevm`/`loadvm`, supply a writable disk backend that supports QEMU
internal VM snapshots, normally a qcow2 image. A raw or read-only disk, or a
VM with no snapshot-capable writable block device, can boot but QEMU may
reject `savevm`; `qmp-smoke.py` reports that QMP error and exits nonzero.

Guest Intel PT probing additionally requires an Intel guest CPU exposing
`intel_pt`, KVM-visible hypervisor evidence, the guest `intel_pt` perf event
source, readable perf policy, and a working `perf` command. Lack of PT support
does not make the harness dishonest; it must be recorded as the exact token
returned by the probe.

Apple Silicon and other Darwin hosts do not satisfy this baseline. HVF,
emulation without KVM, mocks, and CI-only tests are useful development checks
but are not equivalent M0 evidence.

## Tool reference

### `scripts/m0/check-host.sh`

Runs preflight only and prints `host-ready` on success.

| Flag | Default | Meaning |
|---|---:|---|
| `--qmp-socket PATH` | `/tmp/fovea-m0.qmp.sock` | Must not already exist; its parent must be a private, invoking-user-owned mode-700 directory. |
| `--pidfile PATH` | `/tmp/fovea-m0.pid` | Must not already exist; must differ from the QMP path; its parent must be a private, invoking-user-owned mode-700 directory. |
| `--gdb-port PORT` | `1234` | Free loopback TCP port, range 1..65535. |
| `--guest-cid CID` | `3` | Guest vsock CID, range 3..4294967294. |
| `--memory-mib N` | `2048` | Guest RAM in MiB, range 1..1048576. |
| `--cpus N` | `2` | Virtual CPUs, range 1..4096. |
| `-h`, `--help` | | Print help. |

Narrow overrides for tests or explicit tool selection are `UNAME_BIN`,
`QEMU_BIN`, `KVM_DEVICE`, and `PYTHON_BIN`. Production acceptance should use
the real host identity and KVM device, not fake overrides.

The defaults under `/tmp` are retained for CLI compatibility, but normally fail
the private-parent check. Use a private runtime directory for acceptance.

The check rejects non-Linux, non-x86_64, inaccessible KVM, missing tools,
occupied GDB ports, existing socket/pidfile paths, unsafe QMP/pidfile parents,
invalid ranges, a QMP path containing a comma, and conflicting QMP/pidfile
paths.

After the path permission checks, Python opens `KVM_DEVICE` with `O_RDWR`
(`O_CLOEXEC` where available), issues `fcntl.ioctl(fd, 0xAE00)`, the
`KVM_GET_API_VERSION` request, and requires the returned version to equal 12.
The same exact operation applies to an explicitly overridden `KVM_DEVICE`, so
test substitution remains visible rather than bypassing the KVM API check.

### `scripts/m0/run-vm.sh`

Runs the same preflight, then starts QEMU under an attached wrapper that waits
for the child to exit.

Boot flags:

| Flag | Meaning |
|---|---|
| `--kernel PATH` | Readable Linux kernel image for direct kernel boot. |
| `--initrd PATH` | Readable initrd; valid only with `--kernel`. |
| `--disk PATH` | Readable stable regular guest disk attached as virtio; its canonical parent must not be group/other writable. |
| `--append TEXT` | Kernel command-line fragment; repeatable and valid only with `--kernel`. |

VM flags are `--qmp-socket`, `--pidfile`, `--gdb-port`, `--guest-cid`,
`--memory-mib`, and `--cpus`, with the same defaults and ranges as
`check-host.sh`. `--dry-run` performs preflight and prints one shell-escaped
QEMU command without launching. `-h` or `--help` prints help. The same
`UNAME_BIN`, `QEMU_BIN`, `KVM_DEVICE`, and `PYTHON_BIN` overrides apply.

At least one of `--kernel` or `--disk` is required. Supported combinations are:

| Inputs | Use |
|---|---|
| kernel | Direct boot; the kernel command line must make a root filesystem or init available. |
| kernel + initrd | Direct boot with an initramfs. |
| disk | Boot the existing disk through QEMU firmware. |
| kernel + disk | Direct kernel boot with a virtio disk, commonly with an explicit `root=` append. |
| kernel + initrd + disk | Direct boot with initramfs and virtio disk. |

Initrd alone is invalid. `--append` without a kernel is invalid. Repeated
`--append` values are joined with spaces and passed as one QEMU argument.

The generated command uses these exact capabilities:

```text
-enable-kvm
-cpu host
-machine accel=kvm
-m <memory-mib>
-smp <cpus>
-device vhost-vsock-pci,guest-cid=<guest-cid>
-qmp unix:<qmp-socket>,server=on,wait=off
-gdb tcp:127.0.0.1:<gdb-port>
-pidfile <pidfile>
-no-reboot
-nographic
```

It conditionally adds `-kernel`, `-initrd`, `-append`, and
`-drive file=<disk>,if=virtio`. The GDB stub listens only on loopback. The
launcher does not add `-S`, so the VM is not deliberately paused at startup.

Before printing or launching, `run-vm.sh` atomically reserves the canonical QMP
socket path, canonical pidfile path, GDB port, guest CID, and, when supplied,
the disk identity. Disk identity is derived from the canonical regular file's
`st_dev` and `st_ino`, so hardlink and path aliases collide too. These
reservations are held in private mode-700 lock locations. A second invocation
is rejected if any resource is already reserved, even when it uses a different
QMP path. For a real launch, the locks remain until the QEMU child exits; the
wrapper forwards `TERM` or `INT` to QEMU, waits for it, and releases the locks
only afterward. `--dry-run` releases its reservations when the wrapper exits.

### `scripts/m0/qmp-smoke.py`

Interface:

```text
qmp-smoke.py --socket PATH --snapshot NAME [--timeout SECONDS]
```

`--socket` is the QMP Unix socket. `--snapshot` is 1..64 characters and may
contain only letters, digits, `.`, `_`, and `-`, starting with a letter or
digit. `--timeout` is a finite number greater than zero and at most 3600;
default `10`. It bounds the connection and each complete greeting or
command-reply wait using a monotonic deadline, even when asynchronous events
keep arriving.

The client validates the structured QMP greeting, sends
`qmp_capabilities`, then sends these structured QMP requests in order:

```text
human-monitor-command {"command-line":"savevm <name>"}
human-monitor-command {"command-line":"loadvm <name>"}
```

Every request has a distinct `fovea-N` id. Because only one command is
outstanding, any different reply id is rejected. Validated asynchronous event
names are collected without being mistaken for replies, with at most 256
names retained. A sustained event flood therefore still reaches the deadline
with bounded retained memory. Each message remains limited to 1 MiB.

QMP error replies fail normally. For `savevm` and `loadvm`, the QMP return must
also be a string containing only whitespace; non-whitespace HMP diagnostic
text is treated as command failure. Malformed JSON, malformed
greetings/events/replies, timeouts, and disconnects likewise produce a
diagnostic on stderr and a nonzero exit. Success prints exactly one compact
JSON object to stdout containing status, snapshot, commands, and observed
event names.

### `scripts/m0/gdb-smoke.sh`

Connects in GDB batch mode, runs `info registers`, detaches, and prints GDB's
register output.

| Flag | Default | Meaning |
|---|---:|---|
| `--host HOST` | `127.0.0.1` | GDB stub host using letters, digits, `.`, `_`, or `-`. |
| `--port PORT` | `1234` | TCP port, range 1..65535. |
| `--timeout SECONDS` | `10` | Integer connection timeout, range 1..3600. |
| `--vmlinux PATH` | unset | Optional readable symbols loaded with `--se`. |
| `-h`, `--help` | | Print help. |

`GDB_BIN` selects the maintained GNU GDB executable; default `gdb`.

### `scripts/m0/guest-pt-probe.sh`

Run this script inside the guest with no arguments. `UNAME_BIN` is its only
narrow test override. It always exits zero after printing exactly one token:

- `supported`: the guest is Linux x86_64 under observed KVM, exposes Intel PT,
  and `perf record -e intel_pt//u -- true` succeeds.
- `unsupported`: the guest architecture, CPU vendor, or exposed CPU flags do
  not support Intel PT.
- `misconfigured`: invocation, platform, KVM evidence, sysfs/proc policy,
  tooling, the `intel_pt` perf event source, or the actual perf probe is
  unusable.

Record the token verbatim. Do not reinterpret `misconfigured` as
`unsupported`, or either token as a passing PT result.

## Launch and smoke workflow

Use a private host directory owned by the invoking user with mode `700`.
Both the QMP socket parent and pidfile parent must satisfy this requirement.
The disk must be an existing readable stable regular file, not a final-component
symlink, and its canonical parent must not be group/other writable. QMP is an
unauthenticated control socket:

```bash
runtime_dir=$(mktemp -d /tmp/fovea-m0.XXXXXX)
chmod 700 "$runtime_dir"

scripts/m0/check-host.sh \
  --qmp-socket "$runtime_dir/qmp.sock" \
  --pidfile "$runtime_dir/qemu.pid" \
  --gdb-port 1234 \
  --guest-cid 3

scripts/m0/run-vm.sh \
  --kernel /path/to/bzImage \
  --initrd /path/to/initrd \
  --disk /path/to/guest.qcow2 \
  --append "console=ttyS0" \
  --append "root=/dev/vda" \
  --qmp-socket "$runtime_dir/qmp.sock" \
  --pidfile "$runtime_dir/qemu.pid" \
  --gdb-port 1234 \
  --guest-cid 3 \
  --dry-run
```

Review the printed command, then rerun without `--dry-run`. Keep that terminal
attached because the wrapper waits for QEMU and the VM uses `-nographic`.

From separate host terminals:

```bash
scripts/m0/qmp-smoke.py \
  --socket "$runtime_dir/qmp.sock" \
  --snapshot m0-smoke \
  --timeout 10

scripts/m0/gdb-smoke.sh \
  --host 127.0.0.1 \
  --port 1234 \
  --timeout 10 \
  --vmlinux /path/to/vmlinux
```

Inside the guest:

```bash
/path/to/guest-pt-probe.sh
```

The QMP smoke proves only that QEMU accepted an ordered save and load. Task 008
must separately mutate a guest sentinel after `savevm`, perform `loadvm`, and
show that the sentinel returned to its saved state.

## Later real vsock round trip

Task 006 provides `crates/vsock/examples/vsock_guest_ping.rs` and
`crates/vsock/examples/vsock_host_ping.rs`. On Linux, the guest example binds
a supplied CID/port, receives one typed request, and returns a correlated
response plus execution receipt. The host example connects to a supplied
CID/port and verifies both correlated messages.

These examples are the intended basis for the later task-008 real host/guest
vsock evidence. They are referenced here only; this task does not claim that
the examples were built or run across a real VM.

## Cleanup

Stop the attached `run-vm.sh` wrapper with `TERM` or `INT`; it forwards the
signal to QEMU, waits for the child to exit, and releases all reservations.
Confirm the PID from the pidfile is no longer running. QEMU normally removes
its live socket and pidfile. Remove a stale socket, pidfile, or any
`.fovea-launch` directory only after confirming that no QEMU or `run-vm.sh`
process still owns the corresponding QMP path, pidfile, GDB port, guest CID, or
disk. Then remove the private runtime directory and, when empty and unused,
the private global lock root under `TMPDIR`.

Do not reuse or delete the guest disk until any required acceptance evidence
has been captured. `loadvm` intentionally rolls the whole VM back and can
discard guest state created after the snapshot.

## Security assumptions

- QMP can control and alter the VM and has no authentication in this harness.
  Keep both the QMP socket and pidfile in real directories owned by the
  invoking user with mode `0700`; do not expose QMP remotely.
- The GDB stub has no authentication. It is bound to `127.0.0.1`; do not
  forward or rebind it to an untrusted network.
- The disk must be a readable stable regular file whose canonical parent is not
  group/other writable. `run-vm.sh` reserves its canonical device/inode
  identity so concurrent launches cannot use the same disk.
- Kernel, initrd, disk, `vmlinux`, QEMU, GDB, Python, and override executables
  are operator-supplied trusted inputs. The scripts perform no download and
  construct no shell command from guest or QMP data.
- A snapshot is recovery machinery, not a substitute for the host-side audit,
  approval gate, least privilege, or evidence separation.
- Guest output cannot establish host intent or authorize a side effect.

## Troubleshooting

`Linux is required` or `x86_64 is required`
: Move the acceptance run to a Linux x86_64 host. Darwin/HVF is not equivalent.

`KVM device is missing` or `must be readable and writable`
: Load/enable KVM, confirm virtualization is enabled, and grant the invoking
user access to `/dev/kvm`. Do not replace the check with a mock for acceptance.

`KVM_GET_API_VERSION ioctl failed` or `KVM API version is ...; expected 12`
: Confirm the path is the real KVM character device and the running kernel
provides the current KVM userspace API. A readable/writable placeholder file
does not pass preflight.

`QMP socket path already exists`, `pidfile path already exists`, or
`launch resources are already reserved`
: Check for a live QEMU/run-vm process first. The reservation may belong to a
  run using a different QMP path but the same pidfile, GDB port, guest CID, or
  disk. Choose non-conflicting resources for a concurrent run; remove stale
  artifacts only after proving they are unowned.

`QMP socket parent directory security check failed` or
`pidfile parent directory security check failed`
: Use real directories owned by the invoking user with exact mode `700`, and
  pass socket and pidfile paths whose parents are those private directories.

`disk security check failed`
: Use a readable regular disk file that is not a final-component symlink, and
  make sure its canonical parent is not group/other writable. Do not launch
  concurrent VMs against the same disk identity.

`GDB port is occupied or unavailable`
: Stop the existing listener or choose another `--gdb-port`, and pass the same
port to `gdb-smoke.sh`.

`savevm` fails through QMP
: Read the structured QMP error. Confirm the disk is writable and supports
internal VM snapshots, and that QEMU has a device capable of storing VM state.

`QMP peer closed`, timeout, or malformed reply
: Confirm the socket belongs to the intended QEMU, QEMU is still alive, the
timeout is adequate for snapshot I/O, and no other process is proxying or
writing to that connection.

GDB cannot connect or register output is absent
: Confirm the launch used the matching loopback port and a compatible GNU GDB.
Because the VM is not launched with `-S`, it may already be running when GDB
attaches.

PT prints `unsupported`
: Record it exactly; inspect guest architecture, CPU vendor, and `intel_pt`
flag exposure before deciding whether a different physical host is needed.

PT prints `misconfigured`
: Check that the script is running inside the KVM guest, then inspect
`/proc/cpuinfo`, KVM clocksource evidence, `intel_pt/type`,
`perf_event_paranoid`, the installed `perf`, and permissions for `perf record`.
